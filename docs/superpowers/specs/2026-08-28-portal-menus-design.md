# 사내포털 상단 메뉴 설계

**Goal:** AR 포털(`portal.ar.co.kr`) 상단 메뉴 다섯 개 중 넷이 죽어 있다. 눌리게 만들되, 홈에 이미 있는 것을 한 번 더 보여주는 빈 페이지가 되지 않게 한다.

## 지금 상태

`portal.nav`는 `["전자결재","업무관리","인사관리","커뮤니티","마이페이지"]`인데 `portal.navLinks`에는 `{"인사관리":"/hr"}` 하나뿐이다. 링크가 없는 넷은 `<span>`으로 그려져 눌리지 않는다 (`Portal.jsx`의 nav 렌더).

포털은 `site.pages[path]`가 **어떤 필드를 들고 있는지**로 하위 뷰를 고른다. `SUBPAGES`가 그 표다:

| 뷰 | 알아보는 필드 | 뒤로 |
|---|---|---|
| `Attendance` | `attendance` | `/hr` |
| `Menu` | `menu` | `` |
| `Bereavement` | `board` | `/hr` |
| `Leave` | `leave` | `/hr` |
| `Events` | `event` | `/hr` |

`Menu`는 `{title, menu:[{label,path,desc}]}`만 읽는 범용 뷰다. `/hr`이 그걸 쓴다 — 즉 **메뉴 페이지를 하나 더 만드는 데에는 코드가 필요 없다.**

### 전제가 깨지는 지점

홈은 `docs`(4건) · `tasks`(5건) · `news` · `rooms` · `staff`를 **자르지 않고 전부** 그린다. `more="전체보기"` / `more="결재작성"`은 아무 데도 걸리지 않은 장식용 `<span>`이다. 그래서 "전체 목록 페이지"를 그냥 붙이면 홈과 같은 행이 그대로 다시 나온다. 메뉴는 살아나지만 플레이어가 얻는 것이 없다.

소식은 특히 그렇다. `portalFeed`가 그날까지의 `days[n].portal.news`를 앞에 쌓아 5일차에는 21건이 되는데, 그게 전부 홈 한 패널에 들어간다.

## 설계

### 1. 데이터는 한 곳에, 홈이 자른다

`p.docs` · `p.tasks` · `p.news`를 전체로 채우고, **홈 패널이 `slice`** 한다. 메뉴 페이지는 같은 배열을 전부 그린다. 행을 두 벌 적지 않는다 — 한쪽만 고치는 사고가 나지 않게.

- 홈 `내문서` → 최근 4건 + `전체보기` 링크
- 홈 `업무관리` → 최근 4건 + `전체보기` 링크
- 홈 `사내 소식` → 최근 5건 + `전체보기` 링크

`more`는 지금처럼 문자열이 아니라 `{label, path}`를 받아 실제 버튼이 된다. `path`가 없으면 예전처럼 장식으로 남는다.

### 2. 뷰는 `list` 하나만 추가

`SUBPAGES`에 `[List, 'list', '']`를 더한다. 페이지 데이터는 행을 담지 않고 **어느 섹션을 펼칠지 이름만** 든다:

```json
"/approval":  { "title": "전자결재", "list": "docs" },
"/tasks":     { "title": "업무관리", "list": "tasks", "rooms": true },
"/community": { "title": "커뮤니티", "list": "news" }
```

`List`는 홈 패널이 쓰는 행 마크업(`pt-row`, `State`)을 그대로 쓴다. `who`가 있으면 담당이 붙고, `body`가 있으면(소식) 눌러서 본문으로 간다 — 홈의 `setPost`와 같은 경로다. `rooms: true`면 회의실 현황을 옆에 함께 그린다.

이름으로 가리키는 이유: 행 데이터를 페이지에 복사해 넣으면 홈과 어긋난다. 포털이 이미 `p`(= `site.portal` + 그날 것)를 들고 있으므로 `p[page.list]`로 바로 닿는다.

### 3. 마이페이지는 `profile`

목록이 아니므로 `list`를 쓰지 않는다. `SUBPAGES`에 `[Profile, 'profile', '']`를 더한다.

```json
"/my": { "title": "마이페이지",
  "profile": {
    "rows": [["부서", "영업1팀"], ["직급", "대리"], ["내선", "1042"],
             ["메일", "hb.kim@ar.co.kr"], ["재직상태", "재직"]],
    "links": [{ "label": "근태조회", "path": "/hr/attendance" },
              { "label": "휴가신청", "path": "/hr/leave" }] } }
```

`me`의 사번 · 근속 · 총 연차 · 남은 연차는 홈 사이드바와 같은 값을 그대로 읽고, `rows`가 그 아래에 붙는다. 링크는 이미 있는 페이지 둘로만 간다 — 새 화면을 만들지 않는다.

**입사일은 넣지 않는다.** 자연스러워 보이지만 `2017년 04월 12일`은 부름(`summons`)의 정답이고, 사원증 스캔본을 찾아 읽는 것이 그 답을 얻는 길이다. 마이페이지에 적으면 그 길이 한 번의 클릭으로 줄어든다. (위키·포털 비밀번호 `0412`는 이미 포털에 들어온 사람이 아는 값이므로 그쪽은 새는 것이 없지만, 부름 쪽이 얇아진다.)

부름 8단계 중 "포털 마이페이지에 근속 연차가 표시되어 있을 텐데, 대리님은 몇 년차로 나오나요?"가 지금은 존재하지 않는 화면을 가리킨다. 이 페이지가 생기면 그 질문이 실제 화면을 가리키게 된다.

### 4. 콘텐츠

- `docs` 4 → 12건, `tasks` 5 → 12건. 2026년 상반기 과거 건으로 채운다.
- `news`는 이미 날짜별로 쌓이므로 추가하지 않는다.

새 행은 **기존 요청의 답을 담지 않는다.** 포털은 `sites` 안이라 accept가 놓여도 되는 자리지만, 플레이어가 찾아다녀야 할 값이 결재함 목록에 그냥 적혀 있으면 그 요청이 죽는다.

## 테스트

게임이 깨지는 방식을 검사한다.

1. **죽은 메뉴가 없다** — `portal.nav`의 모든 항목이 `navLinks`에 있다. 이번에 고치는 결함 그 자체다.
2. **없는 데를 가리키지 않는다** — `navLinks`의 모든 경로, 그리고 모든 `menu` 페이지의 모든 `path`가 `site.pages`에 실재한다. 하나라도 어긋나면 플레이어는 `notFound` 문구를 본다.
3. **모든 페이지가 그려진다** — `pages`의 각 항목이 `SUBPAGES`가 아는 필드 중 하나를 갖는다. 모르는 모양은 조용히 포털 홈을 그리므로 눈으로는 잘 안 보인다.
4. **`list`가 실재하는 섹션을 가리킨다** — `page.list`가 `portal`의 배열 필드 이름이다.
5. **홈이 자르는 것이 전부가 아니다** — `docs`·`tasks`는 행 수가 홈 slice 수보다 많다. 안 그러면 이 작업이 헛일이다. 소식은 날짜에 따라 쌓이므로 1일차에는 다섯 건이 안 될 수 있다 — 마지막 날 기준으로 검사한다.
6. accept 누출은 기존 검사가 `sites` 전체를 훑으므로 새로 쓰지 않는다.

## 하지 않는 것

- 결재 상세 화면, 결재 작성 폼 — 목록에서 멈춘다.
- 새 ask/objective. 이번 작업은 요청을 늘리지 않는다.
- 소통방(`sotong.ar.local`) 연동. 포털의 `onOpen`은 `site.url + path`로 붙이는 구조라 외부 URL을 못 연다. 커뮤니티는 포털 자신의 소식만 펼친다.
- `staff`(직원 현황)에는 메뉴를 주지 않는다. 상단 메뉴 다섯 개 중 어디에도 해당하지 않는다.
